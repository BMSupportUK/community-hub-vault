# Windows TV Enabler rules

- Discovery reads same-private-host HTTP device descriptions independently of debugging or SSDP responses, retaining missing names as null until all fallback endpoints are tried; this matches phone name lookup without authenticating or changing the TV.

- Enabler presentation uses shared semantic palette roles on both platforms; Windows explicitly honors hidden panels and derives progress only from the existing wizard state, so styling cannot expose other steps or advance checks.

- APK push/install commands get an extended deadline; uncertain app-install replies are reconciled by exact enabled package identity in the current TV profile, so a lost reply is not reported as failure.

- Windows TV Enabler (`windows-tv-enabler/`): isolated Electron, local assets, bundled official ADB; mirrors the phone enabler's wizard step-for-step — `renderer/wizard.js` ports `SetupWizard.java`, both change together; pushes control.apk extracted from the helper download. Unsigned NSIS installer served via `/api/public/tv-enabler-windows` (app_builds row "TV Enabler%Windows").
- After reading the Helper code, never send the TV Home or close BM Remote Helper (both apps): Android only shows its screen-share Allow box while the Helper is in front.
- BM TV Enabler opens on its welcome/PIN screen, then resumes a saved unexpired confirmation at DONE without TV commands; otherwise starts with "What do you need?". Persist the original confirmation expiry, renewal capability and selected TV locally; explicit Reset clears them. Phone and Windows change together.
- Both Enabler apps ask for the 24-hour PIN (customer Settings or ticket/order Remote setup) on every app launch before Get started, never restoring a saved login; `/api/public/enabler-login` swaps the PIN for a device token. Phone and Windows change together.
- A customer-requested renewal uses a per-confirmation secret capability, claimed once; never restart Helper during active/claimed sharing. Only for renewal of a non-active connection, cold-start Helper and keep it foregrounded for fresh consent.
- Both apps persist reference usage reported by the capability-verified refresh endpoint; New code gates use that usage or expiry, never local guesses. This enables another scope without transferring the original binding.
- Install and Screen-share support issue separate references (`enabler_confirm_codes.kind`: install vs share); share references are cleared locally on capability-verified server expiry, including screen-share end, independently of install references and PINs. Only explicit expired responses invalidate saved codes; network failures retain them. Phone and Windows change together.
- Install-only TV progress uses the separate permissionless, launcher-hidden `uk.bmsupport.installscreen` app (`tv-install-screen/`, served by `/api/public/install-screen-apk`, app_builds row "BM Install Screen" kept non-current so it never lists as a customer card); phone `InstallScreen.java` and Windows `installScreenCommand` send identical installing/skipped/complete/error intents, and screen install/display failures are never fatal. Never used in screen-share mode.
- Install our apps lists the install list with current-profile inventory first; customers untick apps (all ticked by default, already-installed greyed and still reported as skipped). Phone `Enabler.picked` and Windows `pickApps` apply the same rule; phone and Windows change together.
- Install references never expire; after Install our apps both Enablers ask "Do you need staff help?": Yes shows the code for the ticket/order, No posts it to `/api/public/enabler-self-install`, which logs code, apps and TV address in the download log and marks it used so New code unlocks. Phone and Windows change together.
